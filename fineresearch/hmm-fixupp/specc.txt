SPECC.TXT
Gemma Trace-Based RL Improvement System

1. OVERVIEW

A service where users:
  - create named gemma versions (e.g. "my-explorer")
  - upload successful pi agent traces to improve their named version
  - chat with their named version via OpenAI-compatible API

Core loop: upload trace -> GRPO + Selective KeepLoRA -> gemma gets a tiny bit better -> chat API

The system makes the named gemma a tiny bit better from each trace.
The trace could be anything. The system is domain-agnostic.
The fact that the user uploaded the trace means it was good.


2. ARCHITECTURE

  User
    v
  API (FastAPI)
    - POST /v1/models/create      -> create named version (new KeepLoRA adapter)
    - POST /v1/traces/upload       -> queue training job
    - GET  /v1/jobs/{id}           -> check training status
    - POST /v1/chat/completions    -> serve named version (OpenAI-compatible)
    - GET  /v1/models              -> list all named versions
    v
  Training Engine (background worker)
    - parse JSONL trace, extract steps
    - filter: skip if gemma already produces similar trace (CSO)
    - generate k=5 rollouts per step using trace as reference
    - score rollouts: +1 if matches expert action, 0 if not (SOD step-level)
    - GRPO loss with high KL regularization (RLS Razor)
    - Selective KeepLoRA weight update (KeepLoRA on gate_proj+up_proj only)
    - sanity check: revert if any metric drops
    v
  Model Registry (SQLite + filesystem)
    - base models: gemma-26b, gemma-31b (shared in GPU memory)
    - named versions = KeepLoRA adapters (.safetensors, ~0.3% of model size)
    - metadata: name, base_model, version, traces_trained, metrics
    v
  vLLM Serving
    - load base model + KeepLoRA adapter
    - OpenAI-compatible /v1/chat/completions
    - vision: accept image_url in messages (screenshot input)
    - hot-swap adapters after training (no dropped requests)
    - multiple adapters served simultaneously (route by model name)

  ]}


4. TRACE FORMAT

4.1 Pi Agent Session (JSONL)
  The trace is a JSONL file from the pi agent (~/.pi/agent/sessions/.../*.jsonl).
  Each line is one JSON event. Events linked by id/parentId forming a chain.

  Event types:
    session:       {"type":"session","version":3,"id":"...","timestamp":"...","cwd":"..."}
    model_change:  {"type":"model_change","id":"...","parentId":null,"provider":"...","modelId":"..."}
    message:       {"type":"message","id":"...","parentId":"...","timestamp":"...","message":{...}}
    compaction:    {"type":"compaction","id":"...","parentId":"...","summary":"...","tokensBefore":...}

  Message roles (inside "message" field):
    user:          {"role":"user","content":[{"type":"text","text":"..."}]}
    assistant:     {"role":"assistant","content":[
                     {"type":"thinking","thinking":"..."},
                     {"type":"toolCall","id":"...","name":"bash","arguments":{"command":"..."}}
                   ]}
    bashExecution: {"role":"bashExecution","command":"...","output":"...","exitCode":0}
    toolResult:    {"role":"toolResult","toolCallId":"...","toolName":"bash",
                   "content":[{"type":"text","text":"..."},{"type":"image","data":"base64..."}]}

  A "step" is the group: (assistant toolCall) -> (bashExecution) -> (toolResult)
  Steps are chained by parentId. Compaction events are skipped.
  Screenshots are base64 PNG in toolResult content with type:"image".

4.2 Reward (generic)
  The trace is a successful session. The user uploaded it because it was good.
  The reward for GRPO is simple: does the model's action match the expert's action?
    +1.0  if model's bash command matches expert's bash command at this step
    +0.5  if model's bash command is similar (same tool, similar target)
     0.0  if model's bash command is different
  This is domain-agnostic. Works for any type of trace.

4.3 Query Extraction
  The initial prompt/query is extracted from the first user message in the JSONL.
  This is used as the starting point for GRPO rollouts.


5. TRAINING PIPELINE

5.1 Parse Trace
  - read JSONL file line by line
  - parse each line as JSON event
  - build event chain by following parentId links (skip compaction events)
  - group events into steps: (assistant toolCall + bashExecution + toolResult)
  - extract screenshots from toolResult messages with image content
  - extract query from first user message

5.2 Extract Steps (ATLAS, 1.4x boost)
  - all steps where the assistant made a toolCall are training instances
  - weight by importance:
      1.0  if step produced significant output (large toolResult, image, or state change)
      0.5  if step is a decision point (navigate, search, extract)
      0.1  if step is minor (echo, ls, setup)
  - discard steps with weight < 0.1
  - ATLAS Table 6: training on weighted steps gives 1.4x over all steps

5.3 Filter (CSO, 1.16x boost)
  - run current gemma on the same query with k=5 rollouts
  - use expert trace history as context (teacher forcing, no live environment needed)
  - if gemma already produces a similar trace (high action match rate): SKIP
  - if gemma fails to match: QUEUE for training
  - CSO Table: expert success + policy failure = 49.5% vs 46.6% for all traces

5.4 GRPO Training (RLS Razor, PaST, OpenClaw-RL)

  For each extracted step in the trace:

    a. construct prompt: conversation history up to this step
       (text messages, bash outputs, screenshots from previous toolResults)
    b. generate k=5 action predictions with current gemma (vLLM, temp=0.7)
    c. score each prediction (step-level reward, SOD 1.4x boost):
         +1.0  if matches expert bash command AND step weight = 1.0
         +0.5  if matches expert bash command AND step weight = 0.5
         +0.1  if matches expert bash command AND step weight = 0.1
          0.0  if does not match expert bash command
       "matches" = same command intent (fuzzy: same tool, same target/path)
    d. compute advantage = score - mean(group of k=5 scores)
    e. GRPO loss = -mean(advantage * log_ratio) + KL_coef * KL(pi, pi_base)
       where pi_base = original gemma before any training
       KL_coef = 0.005 (start), increase to 0.01 if any forgetting detected
       note: GRPO is on-policy, which naturally preserves IFeval better than
       SFT (SDFT 2601.19897: on-policy KL shift << off-policy SFT KL shift).
       the KL reg here serves the same function as SDFT self-distillation.
    f. backprop through KeepLoRA weights only (base model frozen)
    g. KeepLoRA residual subspace projection (see 5.5)

5.5 Selective KeepLoRA Update

  WHY SELECTIVE (not all projections):
    MoE models have gate_proj, up_proj, and down_proj in each expert.
    down_proj is the "unconstrained write-back" that causes output distribution
    drift and routing instability. From Selective Component Tuning (2510.08564):
      Full FT: learn +29.9, forget -27.4
      MLP(Gate&Up only): learn +35.1, forget -2.1  (13x less forgetting, BETTER learning)
    From MoEEdit (2602.10965): FT on MoE causes routing stability RS=23-30%
    (severe disruption). Not touching down_proj avoids this.

  WHY KeepLoRA (not standard LoRA or CURLoRA):
    KeepLoRA constrains LoRA updates to the residual subspace (orthogonal to
    the principal subspace of pretrained weights). This provides:
      - SOTA on MTIL benchmark (Transfer 86.5 vs O-LoRA 82.4, CURLoRA untested)
      - Theoretical guarantee of forward + backward stability
      - Public code: github.com/MaolinLuo/KeepLoRA
    CURLoRA was never tested on MoE, never tested at 26B scale, and does not
    address routing stability. KeepLoRA + selective projection does.

  METHOD:
    1. Apply LoRA ONLY to gate_proj and up_proj (NOT down_proj, NOT attention)
    2. Compute SVD of pretrained gate_proj and up_proj weights to find
       principal subspace (top-r singular vectors)
    3. After each gradient step, project LoRA updates into the residual
       subspace (orthogonal complement of principal subspace):
         grad_residual = grad - (grad @ V_principal) @ V_principal.T
       where V_principal = top-r right singular vectors of pretrained weights
    4. Initialize LoRA A matrix with first-step gradient for plasticity
    5. This ensures new knowledge does not overwrite existing knowledge
    6. MoE router is implicitly frozen (not in target_modules). this is
       intentional for conservative updates. from mechanistic analysis,
       freezing router limits plasticity but prevents routing collapse.
       if more plasticity is needed, unfreeze router with soft L2 penalty
       on gate logits (NOT full unfreeze).

  RESULT:
    - Forgetting prevention: SOTA on MTIL (KeepLoRA) + MoE routing stability
      (freeze down_proj) + KL regularization (R^2=0.96 with forgetting)
    - Base model capabilities preserved: updates are orthogonal to principal
      subspace AND restricted to gate_proj/up_proj only
    - Small adapters: ~0.3% of model size (gate_proj + up_proj only, rank 8-16)

  FALLBACK (if IFeval drops on MoE):
    If Selective KeepLoRA causes IFeval drop on Gemma 4 26B MoE (untested combo),
    switch to MoRAM (2506.21035, ICML 2026):
      - TESTED ON GEMMA (Gemma-2B: BWT 12.65, lowest among 9 methods incl MoE-LoRA 13.56)
      - LLaMA-3-7B: BWT 3.46, lowest among 9 methods (1.5x less than next best L2P 5.25)
      - Highest OP (overall performance) on both Gemma-2B (33.73) and LLaMA-3-7B (43.52)
      - Self-activation routing (no external router = no routing collapse)
      - Rank-1 associative memory atoms (fine-grained, less interference)
      - Public code: github.com/Artificer-AI-Lab/MoRAM
      - LoRA-based (4.4M params, same size as LoRA)
      - Tradeoff: input-dependent routing needs custom serving (not vLLM LoRA).
        merge atoms into single LoRA adapter for vLLM, or use custom backend.
    MoRAM is the most bulletproof alternative because it was actually tested
    on Gemma and eliminates routing collapse entirely via self-activation.

5.6 Sanity Check
  - after training, eval on 3 held-out traces (or replay the same trace)
  - check IFeval (agentic instruction following canary, SFT destroys 74.3->35.3)
  - if action match rate drops > 5% OR IFeval drops: revert to previous adapter
  - otherwise: save new adapter, increment version
  - log: {"version": 8, "reward_before": 0.3, "reward_after": 0.8,
    "kl": 0.003, "loss": 0.045, "steps_trained": 12, "reverted": false,
    "ifeval_before": 74.3, "ifeval_after": 74.1}


6. SERVING

6.1 vLLM with LoRA Adapters
  - load base model (gemma-26b or gemma-31b) in GPU memory (shared)
  - load KeepLoRA adapter for requested model name
  - vLLM supports multiple LoRA adapters simultaneously
  - route by "model" field in request

6.2 Vision Support
  - gemma vision: accept image_url in messages
  - screenshots sent as base64-encoded images

6.3 Hot-Swap
  - when training completes, load new adapter version
  - in-flight requests finish with old adapter
  - new requests use new adapter
  - keep previous adapter for revert
  - swap is atomic from user perspective

6.4 Multi-User
  - single base model in GPU memory
  - each user has own named versions (KeepLoRA adapters)
  - adapters are small (~0.3% of model, ~80MB for 26B)
  - vLLM serves dozens of adapters simultaneously

8. GUARANTEES

8.1 Always Stronger (never weaker)
  - KL reg (R2=0.96 with forgetting): model CANNOT drift from base [RLS Razor]
  - GRPO is on-policy: naturally preserves IFeval (SDFT insight, same MIT lab)
  - Selective KeepLoRA: updates orthogonal to principal subspace (SOTA MTIL)
    AND restricted to gate_proj+up_proj (freeze down_proj for MoE routing)
    [KeepLoRA 2601.19659 + Selective Tuning 2510.08564]
  - MoE routing stability: freeze down_proj avoids RS=23-30% disruption
    [MoEEdit 2602.10965: FT RS=23-30%, avoiding down_proj preserves routing]
  - only successful traces: no negative signal
  - only traces where gemma fails: maximally informative [CSO]
  - sanity check: revert if any drop > 5%

8.2 Compound Boost
  - step-level scoring: 1.4x [SOD]
  - step extraction: 1.4x [ATLAS]
  - trace filtering: 1.16x [CSO]
  - total: 1.4 * 1.4 * 1.16 = 2.27x over baseline GRPO

8.3 Reliable
  - GRPO: used in every reference paper. standard. proven.
  - KeepLoRA: SOTA on MTIL. public code. theoretical guarantee.
  - Selective projection: 13x less forgetting + better learning (2510.08564)
  - vLLM: production-grade. supports LoRA adapters.
  - OpenAI-compatible API: works with existing tools.


9. DATA FLOW EXAMPLE

  1. User creates: POST /v1/models/create {"name": "my-agent", "base_model": "gemma-26b"}
     -> adapter v0 (identical to base gemma-26b)

  2. User uploads trace: POST /v1/traces/upload
     gemma_name: "my-agent"
     trace_file: session.jsonl (a successful pi agent session)

  3. Training engine:
     a. parse JSONL: 20 steps extracted
     b. extract weighted steps: 12 of 20 are significant (weight >= 0.1)
     c. filter: run my-agent on same query, match rate 0.2 -> QUEUE
     d. for each of 12 steps:
        - construct prompt from history + screenshots
        - generate 5 action predictions
        - score: 2 match expert (+1.0), 1 partial (+0.5), 2 wrong (0.0)
        - GRPO loss with KL=0.005
        - update KeepLoRA weights (gate_proj+up_proj only, residual subspace)
     e. sanity check: match rate improved 0.2 -> 0.6 -> save adapter v1

  4. User chats: POST /v1/chat/completions {"model": "my-agent", "messages": [...]}
     -> served by vLLM with adapter v1

  5. User uploads 10 more traces over time
     -> adapter versions: v2, v3, ..., v11
     -> model gets a tiny bit better from each trace
     -> model does NOT forget (residual subspace + KL reg + freeze down_proj)

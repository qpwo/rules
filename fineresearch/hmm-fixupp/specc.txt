SPECC.TXT
Gemma Trace-Based RL Improvement System

1. OVERVIEW

A service where users:
  - create named gemma versions (e.g. "my-county-explorer")
  - upload successful pi agent traces to improve their named version
  - chat with their named version via OpenAI-compatible API

Core loop: upload trace -> GRPO + CURLoRA + step-level scoring -> stronger gemma -> chat API

The system ALWAYS makes the named gemma stronger (never weaker) because:
  - KL regularization prevents forgetting (R2=0.96 with forgetting, RLS Razor)
  - CURLoRA prevents base model degradation (5.44 vs 53896.68 perplexity)
  - only successful traces are used (no negative signal)
  - only traces where gemma currently fails are trained on (CSO)
  - skills are orthogonal across county sites (cosine ~0.00, PaST)
  - sanity check reverts if any metric drops > 5%


2. ARCHITECTURE

  User
    v
  API (FastAPI)
    - POST /v1/models/create      -> create named version (new CURLoRA adapter)
    - POST /v1/traces/upload       -> queue training job
    - GET  /v1/jobs/{id}           -> check training status
    - POST /v1/chat/completions    -> serve named version (OpenAI-compatible)
    - GET  /v1/models              -> list all named versions
    v
  Training Engine (background worker)
    - parse trace, extract critical steps (ATLAS)
    - filter: skip if gemma already succeeds (CSO)
    - generate k=5 rollouts per step using trace screenshots as environment
    - score rollouts step-by-step using 3-point reward (SOD)
    - GRPO loss with KL regularization (RLS Razor, PaST)
    - CURLoRA weight update + orthogonalize (CURLoRA)
    - sanity check: eval on held-out traces, revert if metric drops
    v
  Model Registry (SQLite + filesystem)
    - base models: gemma-26b, gemma-31b (shared in GPU memory)
    - named versions = CURLoRA adapters (.safetensors, ~0.5% of model size)
    - metadata: name, base_model, version, traces_trained, metrics
    v
  vLLM Serving
    - load base model + CURLoRA adapter
    - OpenAI-compatible /v1/chat/completions
    - vision: accept image_url in messages (screenshot input)
    - hot-swap adapters after training (no dropped requests)
    - multiple adapters served simultaneously (route by model name)

4. TRACE FORMAT

4.1 Pi Agent Session (JSONL)
  The trace is a JSONL file from the pi agent (~/.pi/agent/sessions/.../*.jsonl).
  Each line is one JSON event. Events linked by id/parentId forming a chain.

  Event types:
    session:       {"type":"session","version":3,"id":"...","timestamp":"...","cwd":"..."}
    model_change:  {"type":"model_change","id":"...","parentId":null,"provider":"...","modelId":"..."}
    message:       {"type":"message","id":"...","parentId":"...","timestamp":"...","message":{...}}
    compaction:    {"type":"compaction","id":"...","parentId":"...","summary":"...","tokensBefore":...}

  Message roles (inside "message" field):
    user:          {"role":"user","content":[{"type":"text","text":"..."}]}
    assistant:     {"role":"assistant","content":[
                     {"type":"thinking","thinking":"..."},
                     {"type":"toolCall","id":"...","name":"bash","arguments":{"command":"..."}}
                   ]}
    bashExecution: {"role":"bashExecution","command":"...","output":"...","exitCode":0}
    toolResult:    {"role":"toolResult","toolCallId":"...","toolName":"bash",
                   "content":[{"type":"text","text":"..."},{"type":"image","data":"base64..."}]}

  A "step" is the group: (assistant toolCall) -> (bashExecution) -> (toolResult)
  Steps are chained by parentId. Compaction events are skipped (they just drop turns).
  Screenshots are base64 PNG in toolResult content with type:"image".

4.2 Scores (3-point scoring)
  Provided separately in the upload request (or derived by the system):
  {
    "business_docs":      {"found": true, "real": true, "source": true, "source_url": "..."},
    "health_inspection":  {"found": true, "real": true, "source": true, "source_url": "..."},
    "reviews":             {"found": true, "real": true, "source": true, "source_url": "..."}
  }
  source = true means from gov/original, not aggregator.
  If not provided, system derives by analyzing session output for .gov URLs,
  business name matches, inspection dates, and review sources.

4.3 Query Extraction
  The query is extracted from the first user message in the JSONL.
  Example: "lookup Johns Restaurant in Springfield, IL and get all business
  incorporation docs and health inspection and google reviews..."


5. TRAINING PIPELINE

5.1 Parse Trace
  - read JSONL file line by line
  - parse each line as JSON event
  - build event chain by following parentId links (skip compaction events)
  - group events into steps: (assistant toolCall + bashExecution + toolResult)
  - extract screenshots from toolResult messages with image content
  - extract query from first user message
  - extract or receive 3-point scores

5.2 Extract Critical Steps (ATLAS, 1.4x boost)
  - analyze each step's bash command to determine importance:
      1.0  if command output contains a .gov URL matching a scored source_url
      0.5  if command navigates to .gov domain or extracts key data (name, date, etc.)
      0.1  if command is on path (searching, listing, navigating to relevant site)
      0.0  otherwise (setup, echo, ls, cat, etc.)
  - discard steps with weight < 0.1
  - remaining steps are training instances
  - ATLAS Table 6: this gives 1.4x improvement over training on all steps

5.3 Filter (CSO, 1.16x boost)
  - run current gemma on same query with k=5 rollouts
  - use trace screenshots as environment (offline replay)
  - if gemma already achieves total_score 3: SKIP (not informative)
  - if gemma fails: QUEUE for training (expert success + policy failure)
  - CSO Table: 49.5% vs 46.6% for all traces

5.4 GRPO Training (RLS Razor, PaST, OpenClaw-RL)

  For each critical step in the trace:

    a. construct prompt: screenshot + query + action history up to this step
    b. generate k=5 action predictions with current gemma (vLLM, temp=0.7)
    c. score each prediction (step-level reward, SOD 1.4x boost):
         +1.0  if matches expert action AND step weight = 1.0
         +0.5  if matches expert action AND step weight = 0.5
         +0.1  if matches expert action AND step weight = 0.1
          0.0  if does not match expert action
         -0.5  if action goes to aggregator or wrong domain
    d. compute advantage = score - mean(group of k=5 scores)
    e. GRPO loss = -mean(advantage * log_ratio) + KL_coef * KL(pi, pi_base)
       where pi_base = original gemma before any training
       KL_coef = 0.001 (start), increase to 0.01 if any forgetting detected
    f. backprop through CURLoRA weights only (base model frozen)
    g. CURLoRA orthogonalization (see 5.5)

5.5 CURLoRA Update (CURLoRA paper, 10000x less degradation)

  Standard LoRA: h = Wx + (alpha/r) * B @ A @ x
  CURLoRA adds one step after each gradient update:

    after updating B and A, orthogonalize B against all previous B matrices:
      B_orth = B - B @ B_prev.T @ pinv(B_prev @ B_prev.T) @ B_prev
    then set B = B_orth

  Result: base perplexity stays at 5.44 after sequential training.
  Standard LoRA: explodes to 53896.68. Model destroyed.
  CURLoRA: model fine. Always.

5.6 Sanity Check
  - after training, eval on 3 held-out traces
  - if any score drops > 5%: revert to previous adapter version
  - otherwise: save new adapter, increment version
  - log: {"version": 8, "reward_before": 1.2, "reward_after": 2.8,
    "kl": 0.003, "loss": 0.045, "steps_trained": 12, "reverted": false}


6. SERVING

6.1 vLLM with LoRA Adapters
  - load base model (gemma-26b or gemma-31b) in GPU memory (shared)
  - load CURLoRA adapter for requested model name
  - vLLM supports multiple LoRA adapters simultaneously
  - route by "model" field in request

6.2 Vision Support
  - gemma vision: accept image_url in messages
  - screenshots sent as base64-encoded images
  - model sees screenshot and generates text response

6.3 Hot-Swap
  - when training completes, load new adapter version
  - in-flight requests finish with old adapter
  - new requests use new adapter
  - keep previous adapter for revert
  - swap is atomic from user perspective

6.4 Multi-User
  - single base model in GPU memory
  - each user has own named versions (CURLoRA adapters)
  - adapters are small (~0.5% of model, ~130MB for 26B)
  - vLLM serves dozens of adapters simultaneously

[training]
algorithm = grpo
kl_coef = 0.001
group_size = 5
actor_lr = 1e-6
temperature = 0.7
epochs = 1
clip = 0.2
max_prompt = 2048
max_response = 1024

precision = bf16

[curlora]
rank = 8
alpha = 64
target_modules = q_proj,k_proj,v_proj,o_proj,gate_proj,up_proj,down_proj
orthogonalize = true

[filtering]
skip_if_gemma_score = 3
min_traces_per_batch = 1
max_traces_per_batch = 16

[sanity]
revert_if_drop_pct = 5.0
held_out_eval_size = 3

[serving]
vllm_backend = true
max_model_len = 8192
gpu_memory_utilization = 0.9
enable_vision = true

Implementation stack:
  - training: PyTorch + transformers + peft
  - rollouts: vLLM (with LoRA adapter support)
  - serving: vLLM with OpenAI-compatible API
  - API: FastAPI
  - queue: in-memory or Redis
  - storage: filesystem for adapters, SQLite for metadata


8. GUARANTEES

8.1 Always Stronger (never weaker)
  - KL reg (R2=0.96 with forgetting): model CANNOT drift from base [RLS Razor]
  - CURLoRA (5.44 vs 53896.68): base model CANNOT degrade [CURLoRA]
  - only successful traces: no negative signal
  - only traces where gemma fails: maximally informative [CSO]
  - orthogonal skills (cosine ~0.00): no interference across sites [PaST]
  - sanity check: revert if any drop > 5%

8.2 Compound Boost
  - step-level scoring: 1.4x [SOD]
  - critical step extraction: 1.4x [ATLAS]
  - trace filtering: 1.16x [CSO]
  - total: 1.4 * 1.4 * 1.16 = 2.27x over baseline GRPO

8.3 Reliable
  - GRPO: used in every reference paper. standard. proven.
  - CURLoRA: one orthogonalization line. same cost as LoRA.
  - vLLM: production-grade. supports LoRA adapters.
  - OpenAI-compatible API: works with existing tools.


9. DATA FLOW EXAMPLE

  1. User creates: POST /v1/models/create {"name": "county-pro", "base_model": "gemma-26b"}
     -> adapter v0 (identical to base gemma-26b)

  2. User uploads trace: POST /v1/traces/upload {"gemma_name": "county-pro", "trace": {...}}

  3. Training engine:
     a. parse: 20 steps, 3/3 score
     b. extract critical steps: 7 of 20 are critical
     c. filter: run county-pro on same query, gets 1/3 -> QUEUE
     d. for each of 7 critical steps:
        - show screenshot to gemma
        - generate 5 action predictions
        - score: 2 match (+1.0), 2 partial (+0.5), 1 wrong (0.0)
        - GRPO loss with KL=0.001
        - update CURLoRA weights, orthogonalize
     e. sanity check: all 3 held-out traces improve -> save adapter v1

  4. User chats: POST /v1/chat/completions {"model": "county-pro", "messages": [...]}
     -> served by vLLM with adapter v1

  5. User uploads 10 more traces over time
     -> adapter versions: v2, v3, ..., v11
     -> model gets progressively better at:
        - finding .gov sources (not aggregators)
        - extracting real business docs
        - finding real health inspections
        - verifying reviews from source
     -> model does NOT forget previous county sites (orthogonal skills)
